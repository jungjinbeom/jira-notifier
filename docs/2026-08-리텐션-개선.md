# 리텐션 개선 작업 (2026-08-03)

> **배경**: "처음엔 썼는데 이후에 손이 가지 않는다"는 문제를 코드 기준으로 진단하고 개선한 기록.
> 진단 결과 앱의 기능 문제가 아니라 **앱이 살아있지 못하는 구조**가 원인이었다.
> 알림 앱인데 알림이 도달할 확률 자체가 낮게 설계되어 있었다.

기준 버전: `1.4.0` · 대상: `src-tauri/src/lib.rs`, `tauri.conf.json`, `src/hooks/useNotifications.ts`, `src/components/notifications/NotificationList.tsx`

## 진단: 이탈이 일어나던 지점

| # | 문제 | 근거 |
|---|------|------|
| 1 | 창 X를 누르면 **앱이 종료됨** | `CloseRequested` 핸들러 부재. 트레이 상주형인데 상주하지 않음 |
| 2 | **재부팅하면 끝** | `tauri-plugin-autostart` 미사용. 매일 아침 수동 재실행 필요 |
| 3 | 앱을 켜도 **▶를 눌러야** 감시 시작 | `is_polling: false`로 시작, 자동 호출 없음 |

| 6 | 앱에 **남는 게** 없음 | `mark_as_read`가 목록에서 삭제 |

1~3번이 곱해지는 구조였다. **재부팅 → 재실행 기억 → ▶ 누르기** 를 전부 통과해야 가치가 발생했다.

## 1. 트레이 상주 (창을 닫아도 종료되지 않음)

창의 X는 이제 종료가 아니라 **트레이로 숨기기**다. 감시는 계속된다.

```rust
.on_window_event(|window, event| {
    if let WindowEvent::CloseRequested { api, .. } = event {
        api.prevent_close();
        let _ = window.hide();
    }
})
```

X가 더 이상 종료가 아니므로 **종료 수단이 필요**해졌다. 트레이를 `tauri.conf.json` 설정이 아닌 Rust(`setup_tray`)에서 생성하도록 옮겨 우클릭 메뉴를 붙였다. 설정 기반 트레이로는 메뉴/이벤트 핸들러를 붙일 수 없기 때문이다.

- 좌클릭 → 창 열기 (`show_menu_on_left_click(false)`로 메뉴가 뜨지 않게 함)
- 우클릭 → **열기** / **종료**

## 2. 부팅 시 자동 실행

`tauri-plugin-autostart` 2.5.1 추가. 첫 실행 시 `--minimized` 인자와 함께 등록되고, 그 인자로 켜지면 창 없이 트레이에만 상주한다.

```rust
.plugin(tauri_plugin_autostart::init(
    MacosLauncher::LaunchAgent,
    Some(vec![MINIMIZED_FLAG]),
))
```

dev 빌드는 `#[cfg(not(debug_assertions))]`로 제외했다. 안 그러면 `target/debug`의 임시 exe가 부팅에 등록된다.

## 3. 감시 자동 시작

폴링 로직을 커맨드에서 `begin_polling()`으로 분리하고, `PollingHandles`(Arc 묶음)로 상태를 전달해 **커맨드와 앱 시작 시점이 같은 로직을 공유**하도록 했다. `State<AppState>`는 커맨드 안에서만 얻을 수 있어 setup에서 재사용이 불가능했기 때문이다.

저장된 설정이 유효하면 ▶ 없이 바로 감시가 시작된다. 프론트엔드는 `usePolling`이 5초마다 상태를 폴링하므로 헤더 표시등에 자동 반영된다 — **FE 수정 불필요**.

## 4. 트레이 현황 표시

폴링 사이클마다, 그리고 읽음/삭제 시마다 트레이를 갱신한다.

- **툴팁**: `Jira Notifier — 미확인 3 · 미배정 10 · 내 담당 5`
- **아이콘**: 미확인이 있으면 우하단에 빨간 점

Windows 트레이는 숫자 배지를 지원하지 않아 **아이콘 자체를 교체**해야 한다. 별도 이미지 리소스를 두는 대신 기본 아이콘의 RGBA를 직접 조작해 원을 합성한다(`badged_icon`). 어두운 배경에서도 보이도록 가장자리에 흰 테두리를 넣었고, 매 사이클 재계산하지 않도록 `OnceLock`으로 캐시한다.

메뉴 조작은 Windows에서 메인 스레드를 요구하므로 `run_on_main_thread`로 넘긴다.

## 5. 트레이에서 이슈 바로 열기

> **당초 계획은 "OS 알림 클릭 → 이슈 열기"였으나 플랫폼 제약으로 불가능했다.**
> `tauri-plugin-notification` 2.3.3에서 `ActionType` / `register_action_types`는 `#[cfg(mobile)]` 전용이고,
> 데스크톱의 `show()`는 fire-and-forget이다. **데스크톱에서는 알림 클릭을 앱이 가로챌 수 없다.**

대체안으로 **트레이 우클릭 메뉴에 최근 미확인 알림 5건**을 직접 올렸다. 클릭하면 브라우저에서 해당 이슈가 열린다.

```
💬 CS-901 — 결재 첨부파일 다운로드 오류…
👤 CS-902 — 표준계약서 문의
─────────────────
열기
종료
```

메뉴 항목 id에 URL을 실어(`issue:<url>`) `on_menu_event`에서 접두사로 판별한다. 우클릭 → 클릭, 2단계로 이슈에 도달한다.

## 6. 읽음이 삭제가 아니게 됨

기존 `mark_as_read`는 이름과 달리 **삭제**였다.

```rust
// Before
notifications.retain(|n| n.id != id);   // 목록에서 제거

// After
if let Some(n) = notifications.iter_mut().find(|n| n.id == id) {
    n.read = true;                       // 표시만
}
```

`JiraNotification`에는 이미 `read: bool`이 있었고 프론트엔드도 `unread` 클래스로 스타일을 분기하고 있었다. **읽음/안읽음을 구분할 준비는 되어 있었는데 백엔드가 지워버리고 있었다.**

추가로 `notifications.json` 영속화를 넣었다. 기존에는 알림 목록이 메모리에만 있어 앱을 끄면 이력이 사라졌다.

프론트엔드도 맞췄다.
- `useNotifications`: `filter(제거)` → `map(read: true)`, `notification_count`는 유지하고 `unread_count`만 감소
- `NotificationList`: `총 N건 · 안읽음 M건` 표시

목록을 비우는 것은 **전체 삭제** 버튼만 담당한다.

## 작업 중 발생시켰다 고친 회귀

1~3번 구현 시 자동 실행에서 창이 깜빡이는 것을 막으려 `visible: false`로 창을 만들고 setup에서 띄우는 방식을 썼다. 그런데 **Windows에서는 그렇게 만든 창이 최소화 상태(-32000,-32000)로 잡히고 `show()`로도 `unminimize()`로도 복구되지 않았다.** 일반 실행 시 창이 아예 보이지 않는 상태였다.

`visible: true`로 되돌리고, **자동 실행일 때만 setup에서 `hide()`** 하는 방식으로 변경했다. 자동 실행 시 아주 짧은 깜빡임이 있을 수 있으나, 일반 실행 경로의 정확성이 우선이다.

## 미해결 / 확인 필요

**클릭하지 않은 알림이 읽음 처리되는 현상**이 검증 중 세 번 관찰됐다. 마우스를 창 밖으로 옮기고 90초 무접촉 관찰을 했음에도 `[읽음]`이 기록되고 목록이 비워졌다(미확인 6 → 0).

- 코드상 자동 호출 경로는 없다. `markAsRead` / `clearNotifications`는 카드 클릭과 "전체 삭제" 버튼에서만 호출된다.
- 패턴이 **1초 간격으로 하나씩, 마지막에 전체 삭제** 로, 사람이 클릭한 것과 일치한다.
- 검증 중 앱을 반복 재시작하며 창이 화면 앞으로 계속 올라왔으므로, **사용자 조작일 가능성이 가장 높다.**

사용자 조작이 아니었다면 실제 버그이며, 6번의 의미를 정면으로 무너뜨리므로 재현·추적이 필요하다.

## 참고: 디버그 로그

이 앱은 릴리스 빌드에 콘솔이 없어 로그 파일이 유일한 관찰 수단이다(`%TEMP%\jira-notifier.log`). 작업 중 다음 로그를 추가해 두었다.

- `[트레이] <툴팁> (바로가기 n건)` — 폴링 사이클마다
- `[읽음] <이슈키> (<id>)` / `[모두 읽음] n건 처리` — 사용자 조작 시
